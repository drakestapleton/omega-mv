1. Audit of the recorded run (RESULTS.txt, 2026-10-25)
-------------------------------------------------------
- Core class. The protocol says "the GB10 host CPU (Cortex-X925 cores), pinned with taskset to one core".
  run.py pinned `taskset -c 3`. On this host (lscpu, 2026-11-09) cpus 0-4 and 10-14 are Cortex-A725 and
  cpus 5-9 and 15-19 are Cortex-X925. The recorded run therefore ran on an A725 core. RESULTS.txt does
  not declare this deviation.
- Arm B identity. "om2/sha-cutover 0e5f02630" is not an object in the Radicle repository. The merged
  cutover is #776 (merge 7505b3a3, cutover commit 450bbefd). Since then the bridge generator pin moved
  from NATIVE_PIN 24f252b9... to 2c1bf637... and OMC_PIN from 49923639... to 6d1b1cf5.... The SHA unit
  bytes did not change: omc 6d1b1cf5 compiles om/sha256/sha256-om2.om (sha256 dbf002dd...94bb) to the
  qualified artifact 27775fb2...0b (21340 bytes). The generated binding file differs: src/omega_om_units.c
  is sha256 a034f040... at the merge and 693b4ca8... at main. This run does not establish whether the SHA
  call path inside that file changed.
- Undeclared omissions. Load (uptime) was not recorded. Cold first-call times, SHA code size per arm
  (the run reported the whole libomega_gpu.a), static and observed stack, peak RSS and SHA unit compile
  time (median of 41) were not collected. Arm C was NOT_RUN. Only the missing p10 was declared.
- The recorded verdict stays as written: REGRESSION at 1, 31, 32 and 55 bytes; PASS elsewhere. It was
  measured on an A725 core, against a candidate whose exact commit is not in the repository.

Design: seed 20261109; 3 discarded warm-up rounds, then 31 rounds. Within a round the arms ran in a

  checked in two places. The driver compared every timed call. The harness compared the printed digest
  with sha256sum over the same bytes; a mismatch voids the run. Cold: 31 fresh processes per arm for
  64 B and 1 MiB, in seeded order. Compile: 41 interleaved compiles of each arm's unit by its own omc.
Void before data: the first attempt (run-void1.log) stopped in warm-up round 0. The harness oracle
  hashed 2^20 bytes for the 7-byte stream, but the driver's loop feeds whole chunks and hashes
  ceil(2^20/7)*7 = 1048579 bytes. The same holds for bench.c in the recorded run. The oracle was
  corrected and the run restarted from the beginning. No timed round existed before the void.

Verdict under the predeclared policy: REGRESSION at 31, 32 and 55 bytes (+16 to +32 ns per call,
5.3% to 10.5%). PASS at every other size. The protocol reports tiny inputs (0 to 64 B) separately:
here they are the rows hash:0 to hash:64, each judged by its own 1.05 limit, and every regression
above is a tiny input. Bulk (at least 64 KiB) is 0.712 to 0.727: B is 1.38x to 1.40x faster
(Wolfram: N[{1/0.712, 1/0.727, 1/0.494}, 4] -> {1.404, 1.376, 2.024}). A 1 MiB message in 1-byte
chunks is 0.494: B is 2.02x faster. The cold first call on 64 B is 1.364x slower. Mechanism
[INFERENCE, not measured in isolation]: below 56 bytes a call does one
compression in both arms, and the ABI v2 path adds the view setup and the digest copy-out through the
binding. If that holds, the regression sits in the call path rather than in the compression code, and
removing it is a change to the generated binding (omega-bridge). Such a change needs its own run under
this protocol.
NOT_RUN: the static stack of arm A, the observed stack of either arm in this run, and a quiet-host
repetition.
