## Speed
Speed = 2MNK / info.main_ns, one sample per case. main_ns is the host-observed time from submit to the second completion marker, with the marker busy-polled for up to 2000 us (`--spin-us`, default 2000): it includes the
launch/completion latency of the host path (about 8 to 11 us at the smallest shapes) and is not a pure device kernel time. One named measured ceiling per type: BF16 HMMA 115.36 TFLOPS (evidence
OWN30B-T3-TC-PEAK-BW-5faa0f70-20261013T2236Z, peak.log line 9; the peak.log lines are printed by our own tensor-core peak test, "declared 88" registers of our codegen and "sim chains" of our simulator; I did not
trace what fa_ops.cu in that directory is used for) and FP8 e4m3 QMMA 237.52 TFLOPS (the file above).
Final run: best case 0.0552 (bf16, 8192x8192x826 A col B col) and 0.0595 (e4m3, 8192x64x8192 A row B row) of the ceiling; 8192^3 squares 0.0379 to 0.0433 (bf16) and 0.0426 to 0.0453 (e4m3); median over the 108 cases
per type of at least 2^30 multiply-adds 0.0400 (bf16) and 0.0383 (e4m3). Small shapes show a fraction near zero because the time is latency, not arithmetic.
No confidence interval is attached to a case. Repeat data: the 40 large cases per type of the 26-triple list were also measured in the two history runs; against the final run the fraction differs by a median of
5% to 8% (9b77c759 run: bf16 7.8%, e4m3 5.0%; b291375e run: bf16 8.5%, e4m3 6.9%) and by at most 34% (bf16). The final window ran at load1 16.6 (the tool admits a window while load1 is at most nproc = 20, the enforced
limit in spark-window's code; its header comment still says 10, a stale comment outside this repo); the earlier runs were at 9.65 and 13.2. Read the fractions as about 0.04 to 0.06 of the ceiling at the large shapes, not to
two digits. This is the general any-shape kernel, not the L403 tuned prefill kernel; the C3 gate is correctness plus the reported fraction, not a speed target.

## Negative controls, wrong transpose
Mutant 4: `omega_gpu_gemm_drive` packs A with the strides of the other layout. Mutant 5: the same for B. Both read inside the M*K / K*N buffers (no out-of-bounds read). Host, simulator and chip all catch them (above), on
one non-square shape 65x63x100 per type and direction. The original GitHub-only c97e25c (mutant 4, host 166 / sim 188 / control 4 of 188) was not in any local store and GitHub is not used; this is a re-implementation and
extension with the same behaviour. The old C3-GEMM README (evidence/C3-GEMM/README.md, "(next) chip ... waiting for a chip window") is reviewed evidence and cannot be edited (evidence-immutable gate); this directory
supersedes that row, and docs/OMEGA.md points here.
