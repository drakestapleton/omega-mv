## 1. Plain-English summary

The Pi does two jobs at once. It is a small test computer where Aienux has run on real hardware: it reads its memory card, keeps a locked and signed store that survives a power cut while idle (one real run; a cut in the middle of a write is tested in QEMU only), unlocks it with a recovery secret, runs a 1-billion-parameter model at 1.20 tokens per second (a token is roughly a word piece), loads signed programs, and runs Aien's request router (Reflex) on the board. On a branch that is not on `main` it also held signed, encrypted sessions with the Spark over the wired network (11 of 11 on 2026-10-16; section 3). It is the always-on machine ("hub") that keeps the private network running and holds the files of the public websites (that it serves them is INFERRED, high; section 4).

Those two jobs cannot both be done by Aienux today. Aienux has no TCP, no TLS and no way to run the network coordination service or a web server. Every native test so far is a temporary window: the Pi boots Aienux once from its memory card, then goes back to Linux. While a window is open, the tailnet's coordination service is down, and so are the public websites the Pi appears to serve (INFERRED, high: nginx and the site directories are on the Pi; section 4).

Little has changed in the Pi's native code since 2026-10-20: the one addition on `main` is the Reflex router image (#402). The C kernel is frozen since 2026-10-24 (bug fixes only, `native/kernel/README.md` line 3), so new Pi device work is written in Omega. What changed most is the hub itself: two of the services listed in October have stopped, and the 2026-11-15 look found the public website directories on it (October's look did not check for them) (section 4).

Today (OBSERVED, running services on 2026-11-15, compared with 2026-10-20):

| Role | 2026-10-20 | 2026-11-15 |
| --- | --- | --- |

Aienux side (OBSERVED in the repository): pairwise signed transport `native/net/aienos_sec.{h,c}`, a signed and encrypted link between two machines that each know only the other's key (SIGMA-style handshake, X25519, Ed25519, HKDF, AES-256-GCM-SIV; "a pinned roster of one", TEST identities only); reliable channel `aienos_ctl.c`; UDP/IPv4/ARP/ICMP `aienos_net.c`. No TCP, TLS, DNS or DHCP. The Pi to Spark session layer `native/net/pispark.[ch]` exists only on `pi5/net-398-wire` (section 3b). Machine identities issued by an owner root are written in seeded Omega in `native/omega/netid/` (ledger L231): the owner root (Ed25519 on the owner YubiKey, PIV slot 9c, `docs/OWNER_KEY_CEREMONY.md`) issues each machine's Ed25519 credential, TEST credentials and other roots are refused, and the handshake is SIGMA over TCP. It is not on `main`: it is held only under the Radicle-era ref `refs/heads/patches/0de8f71b00c8df8f79d3515beeabc7c95af277a4` (head `b821a0dd`, 2026-11-09), which is history; landing it needs a fresh review and the gates through the current route. Per its README it is IMPLEMENTED and EXERCISED on Linux hosts only: `tests/run.sh` and `tests/twomachine.sh`, the latter between the Spark and this hub, with a stand-in owner key generated for the test; nothing has run on Aienux. Its handshake uses the host's TCP sockets, which `native/net` lacks, so landing it does not by itself give AienOS machines a multi-peer roster: that needs native TCP in Omega (step 9) or the credential check carried onto the signed UDP transport (INFERRED, high; not yet decided). Its README lists wiring into `native/net/aienos_sec.c` as a next step; the C kernel is frozen, so the native side is the Omega transport, not `aienos_sec.c`. The word "gateway" appears in no file under `native/net`, `docs/adr` or `docs/*.md` (other than these two maps); ledger L690 (open) is an Omega chat gateway for Aien, not the network gateway discussed here.

| --- | --- | --- |
| Headscale | A TCP/HTTPS server, TLS 1.3, the control protocol, a database, and relay traffic | **Must move to another always-on machine, or be rebuilt natively.** A native rebuild starts with TCP and TLS, the same gate the Spark's model server needs. TLS and WireGuard primitives come from vetted implementations, never hand-rolled. omega-mv `main` already has HTTP/1.1 client and server units in seeded Omega (`seed/net/http.om`, `https.om`) and a TLS 1.3 client under audit (`om/tls/`, `AUDIT_SCOPE.md`); what is missing is a native TCP stack and a TLS server role. The row is UNKNOWN, not rejected. Experiment: write the control protocol down from Headscale's open source and count the parts that need TCP. Its licence file, read 2026-11-15, is BSD 3-Clause (copyright Juan Font; the copy pinned with the omnet integration is v0.29.6, commit `a2b1d786`) |
| Tailscale client | WireGuard data plane plus the control protocol | Same as above; near term, a subnet route on the Linux hub lets native machines be reached on the home network (INFERRED, medium) |
| Public websites (nginx) | TCP, TLS, HTTP | Moves with Headscale. These sites are public, so a native window takes them offline for its length |
| Secrets, mail, links and tunnels to other sites | TCP and TLS servers; WireGuard (a vetted implementation) | Another machine, or rebuilt natively after TCP and TLS; the links are part of the gateway decision below |
| The remaining operator services | Linux programs | Another machine |
| DNS filter | UDP DNS plus blocklists | If one is wanted, it is the easiest first native service (UDP only for most queries) |

Recommended role (INFERRED, medium): the Pi stays the **always-on Linux hub** until a second always-on machine can carry the coordination service and the websites. Native Aienux on the Pi stays a short attended window, as today. The reason is physical: one board cannot run two operating systems at once, and nothing else currently provides those services.

Gateway (a decision for Drake; no code exists): a machine that speaks HTTPS to people and the signed UDP transport to the AienOS machines. Candidates: the hub (always on, already the tailnet anchor) or the Spark (always on, already the iMac's boot and chat server). The 2026-10-20 draft also named the MacBook; it is dropped here because it is not always on and is the operator's own machine (it writes and reads back the iMac's boot sticks, `docs/IMAC_AIENOS_MAP.md` section 5). A gateway also needs a roster of many peers; `aienos_sec` accepts one, and the owner-issued identities of `native/omega/netid/` (above) are not on `main`.

## 5. Ordered path

Notation: **[H]** host or QEMU only; **[A]** needs an attended one-time boot of the Pi (Linux comes back, and the hub's services are down for the window); **[O]** Drake only. The C kernel is frozen, so new Pi device work is written in Omega; bug fixes to the C kernel are allowed.

1. [A] Run the own Omega model on the Pi from an aien-train `a64efi` build of `main` (PI-M4), its sha256 recorded before the boot, with the answer compared byte for byte to the Spark reference. Builds of the same program already ran with no operating system on the DGX Spark, so it is expected to need no new driver (INFERRED, medium; PI-M4).
2. [A] One lab image, written in Omega (an `a64efi` firmware program like step 1), that prints: a bandwidth loop (PI-M3 a), temperature and fan state (PI14), the RTC value (PI13).
3. [H] UART input and a serial shell; [O] a USB-serial cable (physical) removes the card-file secret from unlock (PI5, PI12).
4. [H] RP1 xHCI model and keyboard class; [A] keyboard on hardware (PI6). This also gives real-secret entry (PI5) and typed input to Reflex (PI22).
5. [H] Network: redo the Pi to Spark session in Omega (receive, ARP, signed sessions), using `pi5/net-398-wire` and the 2026-10-16 r1 and r2 runs as the reference design and the hardware evidence, not as code to land in the frozen C kernel (section 3b). Only a bug fix to `main`'s `pi5_gem.c` or `pi5_net.c` stays C. Then the first signed session from a build of `main`.
6. [H] Multi-core inference, new and written in Omega (for example in the `a64efi` own-model program of step 1): split rows across cores, checked against the reference output; report speed against the measured ceiling (PI-M3 c).
7. [H][A] Wall clock and a fan and thermal rule (PI13, PI14), so a native window can be long.
8. [H] Wi-Fi, Bluetooth, GPIO/I2C/SPI, HDMI (PI15 to PI18): seeded-Omega models and a documentation record already exist on `hive/t_0adfd822-pi5-models` (section 3b); they need a fresh review and landing before any chip code. Firmware loads only with Drake's go.
9. [H] A native TCP stack, then a TLS 1.3 server role (shared with the Spark; omega-mv `main` already has HTTP/1.1 units and a TLS 1.3 client, section 4), then the coordination protocol, one part at a time.
10. [O] Decide the gateway machine and the second always-on machine (section 4). Until then the Pi's native windows stay short.

## 6. Operator steps (Drake only)

None of these is authorized by this document.

- Each native window needs the card's boot menu set for a one-time boot and Linux restored afterwards, as in `docs/native/PREFLIGHT-AND-RECOVERY.md`. The public websites and the tailnet coordination are down while it runs.
- A USB-serial cable from another machine to the Pi's UART header.
- A decision on the gateway and the second always-on machine.
- The same owner-key and release-key steps as the other machines.
- Allow any firmware load (Wi-Fi, Bluetooth) if those rows are built.
